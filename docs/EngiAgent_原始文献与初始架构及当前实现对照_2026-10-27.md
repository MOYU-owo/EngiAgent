# EngiAgent：原始文献、初始架构与当前实现对照

日期：2026-10-27。

> 本文为本轮实施前的比较快照。随后新增的受限专家咨询、自然语言参数补丁、程序角色模式与已执行机制对照，见 `consultation_delivery.md`；本文中的“未实现”保留当时评审语境。

## 1. 对照结论

**当前项目完成了原论文核心设计/验算路径的受限中国规范适配，并把最初架构中的工程依赖、变更重算、输入确认和有限改设等主要机制实现了出来；但没有复现原论文的完整专家咨询、OCR、案例数据库与研究验证体系，也尚未完成最初规划的持久化恢复和多方案偏好。**

不能概括为“全面超过原论文”，也不宜认为“仍只是论文的简单复刻”。更准确的定位是：

> 继承原论文的多角色与确定性工程工具思路，缩小开放咨询范围，将实现重心转向显式工程状态、依赖驱动的任务执行、参数变更一致性与工程师确认。

这份对照中的“新增”仅表示相对论文公开描述和本项目实现的差异，不表示已证明领域首创；“论文未明确说明”不等于其内部程序一定没有该功能。

## 2. 依据与证据边界

三组依据：

1. 用户提供的 Chen 与 Bao（2025）MinerU 全文，重点为 §2.1—2.4、§3.3、§4.2—4.3、§5、§6.1—6.3。
2. `docs/EngiAgent_v1.0.md`，重点为 §2、§6、§8、§12—14。
3. 当前 `engineering/roles.py`、`schema.py`、`dependency_graph.py`、`cn_workflow.py`、中国规范工具、UI 适配，以及规范/验收记录与测试。

上一轮评审已实际复测 131 项测试通过，并核查三个修改场景局部与全量计算一致。本轮聚焦文献和架构的对应关系，没有重新开展付费模型调用、浏览器验收或正式批量对照实验。

MinerU 文本包含 OCR、公式和表格转换问题。本文用于比较架构和已报告功能，不将转换文本中的每个符号、单位或宣传性结论直接视为已经独立验证的事实。

## 3. 先澄清四个容易误判的地方

### 3.1 原论文已有确定性工程工具

论文 §2.3 已将材料、荷载、内力、配筋及验算交给规则计算程序。因而“让 Python 计算，不让模型心算”是继承路线，不是本项目独有创新。

### 3.2 原论文已有长期挠度、交互修改和结构化结果

论文 §4.2 已考虑即时与长期挠度；§3.3 展示改变钢筋规格等交互改设；§4.3 展示梁高从 20 in 增至 24 in；§2.3 已保存结构化中间与最终结果；§5 有执行状态和数据库保存机制。

本项目可以强调把这些能力进一步约束为可复现的程序执行与状态管理，但不能说原论文完全没有这些能力。

### 3.3 本项目的“三 Agent”和论文的“三 LLM”不是同一层次

论文的核心业务角色包括 Dispatcher、Structure Design、Design Evaluation，以及负责后续交互的 Expert Consultation。Code-based Knowledge 在原文已经称为 Component，不应机械地当成独立模型角色。

论文 §2.4 的“三 LLM”特指 Expert Consultation 内部的 primary、verification、integrator。当前 EngiAgent 的三个角色是 Dispatcher、Design、Evaluation，两者不能按数量直接对比。

把知识模块保持为资源是合理架构选择，但原文也已经将其描述为组件，不能将“不设规范 Agent”作为明确超越原论文的贡献。

### 3.4 程序 DAG 主导规划符合最初设计

V1.0 §6.1 明确写道：“工程计算依赖一般是固定的；动态的是任务目标、输入完备程度、需要执行的工具子集，以及参数修改后的失效与重算。”

所以当前由程序生成依赖闭包和拓扑计划，符合原架构，不是实现偏离。上一轮对模型自主规划有限的判断，针对的是研究主张与模型调用价值：不能把规则规划说成模型自主发现，也仍应测试 Design/Evaluation 模型复述计划的调用是否必要。

## 5. 最初提出的改进，究竟实现了多少

### 5.1 工程 DAG、变更失效与局部重算：主要完成

V1.0 §6 要求的核心是：按目标求所需节点、按工程依赖执行、修改参数后只重算受影响部分，阻止旧结果误用。

当前 `dependency_graph.py` 给出工具直接字段与条件依赖，`build_plan` 求祖先闭包及拓扑序；`cn_workflow.py` 将实际输入、上游输出、工具/规范配置纳入哈希，再决定执行或复用。

它采用执行过程中比较输入签名的简单方案，不是完整实现所有规划草案中的独立失效引擎、预先 stale 节点表等接口。就有限范围的核心行为而言已经落地；就细粒度性能优化与独立模块化而言仍可完善。

上一轮实际核查：已有梁 11 个验算节点中，梁高修改重算 10、复用 1；裂缝限值修改重算 1、复用 10；活载修改重算 7、复用 4。三者均与全量工具输出一致。这说明实现有效，但不是正式提速统计。

相对论文的准确表述应为：“将参数修改后的依赖与缓存有效性明确编码并可视化、测试。”不要说论文只能每次全部重算，正文不足以支持该断言。

### 5.2 Evaluation 作为设计闭环关口：主要完成

原论文有新设计与已有设计评价两个路径，设计工具也带条件检查；但公开流程没有明确展示与当前相同的、每次新设计均进入 Evaluation 并按预算自动返回的外层控制算法。

当前设计后使用实配方案重新运行验算，失败时可进入有界循环；不开启自动改设则停止并报告。改设成功、预算耗尽都有记录。

因此新增重点是“显式反馈闭环与终止约束”，不是“首次增加一个验算 Agent”。同时，设计和验算共用代码，仍需外部工程验证。

### 5.3 正常使用与中国规范适配：已完成限定范围

当前已有材料、荷载、受弯、受剪、适用构造、裂缝与长期挠度链；比早期仅采用教学弹性挠度的版本有实质进展。

相对论文应区分：

- 长期挠度：原文已有，是按不同规范实现的对应能力。
- 裂缝宽度：原文正文重点展示挠度，未展示与当前同样的独立中国规范裂缝检查链；可以列为本项目明确实现的检查扩展，不能由此断言原系统内部绝无裂缝能力。
- 构造：双方都有部分规则，不能仅看本项目检查名更多就宣布更全面。
- 中国规范：属于适用体系转换与开发验证工作，不能把 ACI 数值直接作为中国规范结果真值。

### 5.4 人工确认：业务完成，持久化机制未完成

原计划的业务目标是防止提取错误直接进入工程计算。当前参数表、修改、校验、确认哈希、变更撤销确认已经实现，满足第一层目标。

原计划还要求通过 LangGraph interrupt/resume 与持久化 Checkpointer 恢复。当前工程图没有接入，UI 内存状态也不能跨进程恢复。

应评价为“确认业务已完成，持久化人机协同未完成”，而不能笼统说 HITL 全部完成或完全没做。

### 5.5 工程师偏好与多方案：未完成

手动改参数、修改一次后出现新结果、保留三轮历史，都不是多个已校核方案的并列选择。原规划 §8.2 还包括偏好变成显式约束、候选比较与再求解，这部分仍缺。

### 5.6 规划中的自然语言参数增量与解释任务：部分未完成

V1.0 提到 modify_design、explain_result 与 Delta Parser。当前 `TaskRequest` 只有 new_design、evaluate_existing、unsupported；参数修改主要通过表格、受限 CLI 编辑及 `revise` 接口。

因此已具备变更计算机制，但没有完整实现“基于当前工程状态的连续自然语言修改、澄清和结果问答”。把任意自然语言重新解析成一个新任务，不等于保留原状态的工程对话。

### 5.7 缺失参数处理：阻断完成，最大可执行子流程未完整实现

论文 §2.3 强调信息不完整时尽量完成可执行步骤；V1.0 也规划了 ready/blocked/missing 等细化行为。

当前会按目标计算必需字段，局部抗弯无需无关荷载等字段，这是实质能力。但所选目标缺关键输入时，确认阶段会阻止运行，并不会普遍先执行材料、几何等所有可做部分，再等待补充恢复。

所以“缺项识别和阻断”已完成，“不完整任务中的尽量推进与恢复”仍是部分完成。

## 6. 原规划中主动舍弃与尚未完成的内容

### 6.1 主动简化：Expert Consultation 的三 LLM 管线

这是最重要的能力取舍。收益是范围更易控制，已支持的改动可统一进入程序工具、确认和再验算；代价是失去原文展示的开放式解释、策略讨论、环境变化咨询和灵活方案探索。

当前 DAG 和报告能回答“算了什么、为什么重算、哪个检查未通过”，尚不能完整替代“为什么这样设计、有哪些经济施工策略、某项规范背景如何理解”的咨询服务。

建议结题前不直接复制整个三 LLM 系统；若需要补充，可先实现受限 explain_result：只读取已算结果和已核验依据，不自由生成新数值。涉及方案改变时，生成参数补丁并走确认与重算。它是建议，当前未实现。

### 6.2 主动限缩：完整规范问答、复杂结构与工业联动

不做通用规范问答、不做多层框架、复杂抗震、施工图或 BIM/有限元联动，符合 MVP 的限缩。原论文自身也把更复杂构件和行业软件集成列为未来方向，不应把这些都算成本项目相对论文的落后。

### 6.3 暂缓而非舍弃：OCR、持久化、多方案、正式实验

这些在最初架构里仍有位置。尤其正式实验本来就是研究验收内容，不能以“为了简单主动舍弃”为理由视为已完成；跨进程恢复和多方案也仍属于明确欠项。

## 7. 与原论文相比，当前哪里更明确、哪里仍不足

### 更明确的实现与展示

- 参数变更到节点失效、复用和结果的对应关系。
- 目标相关子图、缓存条件和修订过程的程序证据。
- 输入提取后的人工确认与变更重新确认。
- 设计失败到有限改设和停止的显式状态控制。
- 中国规范选定条款的计算链与裂缝检查。
- DAG、工具输入输出、修订差异的专门审计视图。

这些支持“实现更显式、可检查”，尚不自动支持“更快、更可靠、更准确”。

### 原论文已展示、当前尚不具备或证据较弱

- OCR 与手绘图片输入。
- 多轮专家咨询及其三 LLM 数值校正。
- 更灵活的改筋、改高、环境约束与策略讨论案例。
- 满意案例数据库保存/检索的功能描述。
- 30 个梁的外部软件验证与模型、时间、成本比较。

原论文的研究证据也应保持审慎阅读：其三 LLM 比较主要针对咨询数值校正，不等于证明设计/验算多角色一定优于单角色；软件数值相关性也不等于完整工程安全证明。本项目补实验时应明确误差容限和失败类型，而非照搬结论措辞。

## 9. 应如何形成可靠的文献比较实验

### 9.1 分开比较功能、机制与数值

功能：按本报告矩阵说明继承、删除与扩展。

机制：在相同中国规范工具上比较固定全量、按需 DAG、DAG+缓存，以及有/无模型角色调用。它们是本项目构建的基线；不能称为原论文原始系统，除非真正获得和运行原系统。

数值：ACI 与中国规范材料、组合、承载和正常使用模型不同，不宜用同一梁的数值差异直接判定谁更准确。可以各自对本规范下独立真值比较，再比较任务完成与交互成本。

### 9.2 三个最值得验证的假设

1. 显式依赖与版本管理能否在连续变更后保持与全量结果一致，并避免过期结果误用？
2. 输入确认能否有效发现关键提取错误，所增加的人工作业时间是多少？
3. 有限自动改设是否能减少人工重试；其动作范围、成功率及材料代价是什么？

如果追加经验学习，应单列第四个假设，采用未见案例验证迁移。它不是当前项目已经具备的相对论文优势。
