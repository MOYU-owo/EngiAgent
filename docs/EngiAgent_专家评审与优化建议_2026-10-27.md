# EngiAgent 专家评审与优化建议

评审日期：2026-10-27。对象：当前工作区版本及“建立 Engiagent 项目”聊天中的交付记录。

## 1. 总体判断

**项目已形成具有演示与教学价值的工程研究原型；核心工作流完成度较高，但科学研究的证据链明显落后于软件功能的完成度。**

作为课程项目，现有工作有较好的实施基础，适合进入结题打磨阶段；作为研究成果，目前能证明“限定范围内的系统可以运行”，尚不足以证明“多智能体优于单智能体或规则程序”“系统使用后学会了工程策略”“局部重算带来显著的端到端提速”。论文级的贡献仍需对照实验、外部工程复核与明确的研究问题支持。

现阶段最值得投入的是：**冻结支持范围与研究主张，补齐对照和消融实验，再把真实证据组织成有辨识度的演示。**

### 评审依据与范围

- 查看了项目设计、技术现状、规范任务、公式复核、独立算术基准、实验协议及 UI 验收文档。
- 检查了角色提示、工程 DAG、缓存、改设、状态判定和相关测试代码。
- 检查了现有工程输出与工作台、DAG 的历史实测截图。本轮没有重新进行浏览器交互验收。
- 本轮重新执行全部测试，结果为 **131 passed in 14.27s**。这些是软件回归测试，不是 131 个独立工程案例，也不等于模型准确率。
- 本轮另外在内存中运行三个已有梁修改场景，比较局部重算与全量计算的全部工具输出。
- 真实 DeepSeek 链路依据既有运行产物及验收记录；本轮未重新调用付费模型。
- 本评审不是对全部结构规范条款的独立认证；公式已有核对记录与算术测试，但仍需要外部工程专家及独立实现复核。

## 2. 进展与完成度

不宜给出单一“完成百分比”：限定构件原型、完整原规划、科研验证、工程产品的验收尺度不同。

|维度|当前判断|已完成的证据|主要缺口|
|---|---|---|---|
|需求理解与输入确认|已形成可用闭环|自然语言/JSON、单位与来源、缺项检查、人工确认、变更撤销确认|复杂歧义、冲突输入、分布外需求尚无批量评价|
|限定中国规范计算|核心链已实现|受弯、受剪、适用构造、裂缝、长期挠度；公式与条文映射|范围有限，缺少多组外部独立基准与工程师签核|
|新设计与已有梁验算|已实现|双入口，实际配筋重新验算，分项与总体状态分离|共用底层公式，不能消除共同计算缺陷|
|DAG 与局部重算|已实现机制|依赖闭包、拓扑顺序、输入/版本哈希、缓存复用、结果一致性|尚无系统效率统计，复杂昂贵工具下的收益未验证|
|有限自动改设|已实现窄范围闭环|成功与达到轮次上限停止的案例|策略以同直径增加纵筋为主，缺少针对失败原因的动作选择与最优性评价|
|人机协同可视化|主要页面已交付|参数、二维梁、LaTeX、Agent 事件、DAG、修订比较与导出|现场演示节奏、关键变化突出、真实下载落盘验收仍可完善|
|研究评价|有协议，缺结果|已明确人工、通用 LLM、固定程序、EngiAgent 对照思路|正式批量对照、消融、统计与失败分析尚未完成|
|跨任务经验学习|未实现|未见工程工作流中的持久经验提炼、检索与策略改进闭环|缓存、历史修订与原 Demo 会话记忆均不足以证明学习|
|原规划扩展|部分未完成|当前进程内状态与历史可查看|OCR、跨进程恢复、多候选偏好等未完成|

**完成度结论：限定梁的核心功能闭环已完成；完整研究验证尚未完成；生产工程能力仍有明显距离。**

文档管理存在一个影响汇报可信度的问题：`EngiAgent_技术现状与规划对照.md` 仍以早期教学 MVP 为基线，其中 DAG、中国规范和 UI 的状态已经落后于实际代码。建议明确标为历史快照，新增统一的当前功能矩阵，避免评委看到互相矛盾的进展描述。

## 3. 科学性：基础合理，主张应与证据相匹配

### 3.1 值得保留的设计

1. **语言理解与确定性计算分工明确。** 工程数值不依赖模型自由生成，公式和条件可以追溯、检查和回归。
2. **状态与参数有明确约束。** 单位、来源、确认状态和修订保护能降低参数误读后直接进入计算的风险。
3. **修改后结果失效具有明确机制。** 工程依赖、上游输出及版本进入缓存判断，比单纯保留聊天文本更适合管理工程变更。
4. **没有把“工具执行成功”混同“工程验算通过”。** 也保留请求项目通过和完整工程审查未完成的区别。
5. **已有边界与异常测试。** 不通过、缺项、工具错误与达到改设上限均有终止路径，避免只展示成功案例。

这些是可信工程软件的基础，也能形成研究对象，但需要实验说明每种机制解决了什么问题。

### 3.2 当前最容易被质疑的研究主张

**（1）多 Agent 的必要性没有得到证明。**

`roles.py` 中，Design/Evaluation 被要求“必须原样返回 required_steps 的顺序，不增删工具”；`workflow.py` 再校验模型返回顺序。`cn_workflow.py` 先调用程序 `build_plan` 生成计划，再把该计划交给模型。

因此，当前动态工具子图确实会随任务和输入改变，但主要由工程规则及 DAG 驱动。模型主要承担需求提取及受约束的角色调用，不能把这一实现描述成“大模型自主发现最优计算路径”。

建议把架构表述为“工程依赖约束下的角色分工与状态编排”。为 Design/Evaluation 的模型调用增加有价值的决策职责，或在低价值路径中移除调用；先做消融再决定。规则程序优于多次模型调用也是有价值的实验发现。

**（2）验算的流程独立性不等于计算实现独立性。**

Evaluation 不直接接受 Design 的通过结论，这一点合理；但二者仍使用同一套材料表和部分底层公式。共同错误可能被两边重复认可。应使用独立人员的计算书、公开例题或另一套实现构建外部真值，特别是裂缝、长期刚度、受剪与构造边界。

**（3）缓存复用不等于学习。**

输入相同而复用旧结果，只证明缓存有效；同一任务失败后按固定规则加筋，只证明搜索循环有效。当前未见跨任务经验导致后续决策改善的证据，不能声称模型持续掌握了结构知识。

**（4）有限改设不等于设计优化。**

当前核心动作是增加同直径纵筋根数；未固定梁高在特定条件下可以增加。它可以处理部分承载、裂缝与挠度问题，但不能自然覆盖锚固、净距、保护层或受剪截面不足。达到三轮上限应表述为“当前候选范围与预算内未找到可行方案”，不能推断问题在工程上无解。

“优化”还需要目标，例如钢筋量、混凝土量、梁高、成本或修改次数，以及与其他可行方案的比较。当前更准确的名称是“有界可行方案搜索”或“有限自动改设”。

**（5）效率论证必须区分节点数量和真实耗时。**

本轮使用既有梁模板、离线固定角色，在同一计算状态上分别修改单个条件，得到：

|修改场景|重新执行工具数|复用工具数|全部工具输出与全量计算一致|
|---|---:|---:|---|
|梁高 550→600 mm|10|1|是|
|裂缝限值 0.30→0.25 mm|1|10|是|
|活载 5→6 kN/m|7|4|是|

每个场景均涉及 11 个验算工具节点。这些是机制核查，不是正式批量效率实验。它们表明收益具有明显的修改类型依赖性。当前工具多为轻量公式计算，哈希、状态管理和网络模型调用可能抵消节省，需实测后才能说总体更快。

此外，当前把上游完整输出纳入哈希，是偏保守的失效策略。后续若确有性能瓶颈，可细化到输出字段依赖；现阶段不宜为减少几个毫秒而增加过多复杂度。

## 4. 研究意义、价值与创新定位

### 4.1 研究意义成立的地方

项目对应一个真实问题：自然语言需求、参数反复修改和工程审核需要被转成可验证的软件执行状态。其研究意义更适合表述为：

> 在限定 RC 梁任务中，研究如何将自然语言交互、显式工程依赖、确定性验算和人工确认结合，降低输入误解、漏验算与变更后旧结果误用，并保持过程可追溯。

这里的重点是工程交互与执行可靠性。结构公式本身不是本项目提出的新理论。

### 4.2 分层评价价值

- **课程与教学价值：较高。** 可观察参数、公式、工具与失败反馈，能连接结构设计知识和 Agent 系统实现。
- **工程辅助研究价值：有潜力。** 参数确认、限定验算、变更传播和审计具有实际意义，需用工程师任务实验验证收益。
- **方法创新：当前证据有限。** 多角色、确定性工具、图编排与缓存均有既有基础，组合应用需要通过清晰问题和实验体现贡献。
- **通用结构设计能力：尚不能据此推断。** 单跨、简支、矩形、均布、单层配筋和指定环境等边界较窄。
- **正式工程替代价值：当前不足。** 节点、施工、耐久、防火与多种作用不在完整审核范围内。

Chen 与 Bao 的既有研究已经包含多 Agent、确定性工程工具、设计/验算双入口、GUI 与工程案例验证，因此这些元素本身不宜列为本项目的原创突破。其论文还明确提出需要比较多 Agent 与统一 Agent 的收益；这恰好是本项目可补充的研究问题。[论文原文](https://www.sciencedirect.com/science/article/pii/S0926580525003711)

### 4.3 最有希望形成特色的三条主线

|主线|当前可展示的内容|成为研究贡献还需要什么|
|---|---|---|
|工程变更下的依赖一致性|目标子图、参数修改、失效与复用、全量结果对照|多种修改及连续修改实验，过期结果误用率与复算代价|
|有边界、可追溯的中国规范执行|条文/公式/工具/结果映射，项目规则与规范要求区分|独立工程基准、条款覆盖矩阵、边界复核|
|工程师可控制的交互闭环|原值/单位/来源、人工确认、修订与失败反馈|输入纠错率、介入次数、审核时间和认知负担评价|

这些应称为“本项目特色及待验证贡献”。是否具有学术新颖性，还需要更系统的文献对比，不能仅凭本次聚焦阅读断言首次提出。

## 5. 对中期专家意见的逐条回应

### 5.1 “AI 能否不断学习，是否学会调截面策略”

应把问题拆成三个层次：

|层次|证明对象|当前情况|
|---|---|---|
|同一任务内反馈改设|根据失败继续尝试|已有固定策略，不能据此证明学会策略|
|跨任务经验复用|历史经验改善新任务的动作选择|尚未实现与验证|
|模型参数学习|权重更新后能力改变|原规划未包含，无需为结题临时上微调|

如果时间紧，建议把“持续学习”明确列为未完成研究问题，优先完成当前机制的对照实验。如果必须回应，可做一个范围小、可测量的外部经验记忆实验：

1. 用工程工具验证过的案例生成经验条目，记录输入条件、失败项、修改动作、结果、适用边界及规范版本。
2. 经工程师审核后持久保存，不把模型自由总结自动升级为规范事实。
3. 在未见过的新案例中检索适用经验，让模型在明确白名单中建议动作，程序仍负责约束检查与重新验算。
4. 比较固定规则、无经验模型、正确经验模型、无关或打乱经验模型的效果。
5. 报告首次改设成功率、达到可行方案的轮次、无效动作次数、最终可行率和端到端耗时。

训练/经验集与测试集应按场景族或参数区间隔离；测试中关闭结果缓存或对各组保持一致。相同案例重复调用变快不足以证明迁移。若经验组只减少轮次而检索与提示使总耗时更长，应如实分别报告。

该路线可称为“外部经验记忆辅助的策略迁移”，不声称基础模型权重被更新。Reflexion 使用反馈与情景记忆，Voyager 使用可积累的技能库，提供了无需即时微调的研究参照；它们不是结构工程有效性的直接证据。[Reflexion](https://arxiv.org/abs/2303.11366)；[Voyager](https://arxiv.org/abs/2305.16291)

### 5.2 “使用了什么规范，全部还是部分”

汇报应专门用一页覆盖矩阵展示：当前采用 GB/T 50010 的 2015 正文与 2024 修订基线，结合 GB 55001、GB 55008、GB 50009 中相关要求；实际只编码支持构件范围内的选定条款。

每行对应“检查事项—规范版本/条款—适用条件—已实现工具—外部验证证据—未覆盖事项”。材料、荷载、受弯、受剪、裂缝、挠度、构造分别列出；初选 L/12、取整、改设步长属于工程经验或项目规则，应单独标记。

不要使用“导入了整本规范”“全面符合中国规范”等表述。还应区分条文已阅读、公式已编码、边界已测试、外部已验证四种状态。当前规范文件核对完成，不等于全部规则被软件实施。

### 5.3 “可视化非常重要”

现有工作台风格与信息架构已有基础。下一步主要提升“变化能被一眼看懂”：

- 参数修改后，立即突出原值、新值和受影响子图；复用节点保持稳定，重算节点依次显示实际事件。
- 改设展示每轮失败项、采用动作、配筋与梁高变化，以及裂缝/挠度相对限值的位置。
- 规范复核形成可阅读的公式、数值代入、单位、条款和结果闭环；不能只有通用公式与原始 JSON。
- 把已经完成的 Agent 调用轨迹与实时运行进度明确区分，避免观众把静态历史图理解为模型正在自主推理。
- 只展示真实采集的计时与调用统计，未采集的指标留空。

不必临时扩大到三维、BIM 或复杂动画。对这个项目，真实参数变化、DAG 差异和失败转通过，比装饰性画面更能说明特色。

### 5.4 “项目能做什么、为什么比别人好、创新点”

“能做什么”已有演示条件；“为什么更好”目前仍是待验证假设。建议准备两张对照表：

1. **与参考论文对照：** 继承了什么、对中国规范做了什么适配、增加了哪些依赖与变更机制、哪些功能仍弱于或未覆盖参考系统。
2. **与同内核固定程序/单 Agent 对照：** 自然语言理解、完成率、变更一致性、人工投入和总成本的实测结果。

不要借用参考论文的准确率、节时率作为本项目成绩，也不必把每个界面功能都写成创新点。

## 6. 优先修改建议与验收标准

### P0：结题前必须完成

|工作|建议实施|验收标准|
|---|---|---|
|统一研究口径|清理“自主规划、独立验算、学习、优化、合规”的边界；标明旧文档快照|README、报告、页面和汇报对同一能力描述一致|
|外部工程验证|选择多组不同控制因素案例，交由独立计算书/公开例题/另一实现复核|关键数值、分项结论与适用条件逐项有依据；差异可解释|
|批量自然语言评价|完整、缺项、冲突、单位混合、不支持工况等分层测试|字段级提取、关键错误、拒答/澄清、端到端完成率分别报告|
|DAG 消融|同输入和同内核比较全量、按需但无缓存、按需且缓存|所有可比数值与结论一致；节点、CPU 与总耗时分开统计|
|角色消融|Dispatcher 后直接程序执行，与当前多角色方案比较|统计完成率、计划失败、模型调用与延迟；据结果保留或缩减角色|
|一条完整演示故事|自然语言→人工确认→计算失败→改设→修改→局部重算→规范复核|现场每个结果能回到原始记录，成功与停止案例都有录像备份|

### P1：最能增加研究深度

1. **改设动作与失败项对应。** 抗弯不足可选配筋/高度，受剪问题检查箍筋或截面，净距不足调整布置/直径或宽度，锚固不足不应继续单纯加筋。只实现支持且可验证的动作，超出范围明确转人工。
2. **小范围候选比较。** 用几种实际可施工的配筋/截面组合比较钢筋量、混凝土量与梁高，形成最简单的目标函数，再讨论优化。
3. **经验记忆研究。** 若将其列为主贡献，必须完成跨任务持久记忆、检索与隔离测试，不能只增加一个历史案例展示页。
4. **人机协同评价。** 测关键错误被发现的比例、确认所需时间和人工操作数；同时记录确认大量参数带来的负担。

### P2：核心结论稳定后再做

OCR、跨进程恢复、复杂构件、BIM/有限元联动、三维展示。跨进程恢复对产品可用性有价值；是否优先取决于演示与实际使用需要，不应挤占研究验证时间。

## 7. 推荐的最小实验设计

现有 `cn_experiment_protocol.md` 是合理起点，但“固定程序 vs EngiAgent”仍不能单独分离多角色、DAG 和缓存的贡献。

|组别|主要用途|
|---|---|
|A 通用 LLM，无专用工程工具|评价自由生成方案与工程规则执行之间的差异；能力与成本边界明确|
|B 同内核固定 Python 全量流程|隔离工程工具本身的正确性与计算成本|
|C Dispatcher + 确定性 DAG/程序角色|隔离自然语言理解和依赖编排的价值，避免多余角色调用|
|D 当前完整 EngiAgent|与 C 比较多角色模型调用是否带来收益|
|E 可选经验增强版本|与相同动作空间的无经验组比较跨任务经验的作用|

对 C/D 再分别开关缓存，避免把所有机制捆在一组。人工组用于评价工程师总工作量，可在代表性子集开展；参与者经验、训练与任务顺序要记录并尽量平衡。

建议先做一轮约 40—60 个、分层覆盖的探索性任务。这个数量是执行规模建议，不是统计充分性的保证。任务应包括完整设计、已有梁、局部验算、单位与自重、缺项冲突、边界/超范围、改设成功和预算耗尽、连续多次修改。覆盖不同跨度、材料、截面与控制项，不能全部由一个模板轻微改写。

关键指标：

- **工程正确性：** 关键中间值误差、分项判定一致率、关键漏项、错误通过率；真值由独立复核确定。
- **输入可靠性：** 字段提取准确率、关键字段错误、缺项/冲突识别与人工纠正成本。
- **系统完成：** 成功完成、工程不通过、正确拒绝、模型/工具错误分别统计，不能合并为一个准确率。
- **变更一致性：** 局部/全量输出一致、旧结果误用、执行/复用节点数。
- **效率：** 纯计算、编排、模型请求、人工交互及总时间分别记录；Token、API 调用和费用在可得时采集。
- **改设质量：** 可行率、轮次、无效动作、材料用量或其他明确目标。

锁定模型和提示版本、公式配置、依赖版本和案例哈希。概率性组预设重试预算并重复运行；同一任务对各组配对比较，报告样本数、原始分布与不确定性。区分冷启动与缓存热运行。零需求附近不宜只用 MAPE；整数配筋差异应结合承载与成本解释，不能机械按数值误差排序。

## 8. 期末汇报组织建议

建议围绕八个问题组织：

1. 工程师在自然语言需求与反复修改中遇到什么问题？
2. 为什么只让 LLM 直接回答或只用固定表单各有不足？
3. 本项目如何划分模型、程序和工程师的职责？
4. 当前用了哪些规范、实现哪些条款、边界是什么？
5. 一个真实案例如何从需求走到可复核结果？
6. 修改后哪些重算、哪些复用，失败后如何改设和停止？
7. 相同条件下，对照实验发现什么优势、代价与局限？
8. 相对于参考工作，本项目真正增加了什么，仍未解决什么？

可选标题：**面向 RC 梁设计变更的工程依赖驱动人机协同智能体系统**。若经验实验真正完成，再考虑在题目中加入经验复用；未完成时不使用“自学习”。

评委最可能追问的四个问题应提前准备证据：

- 拿掉 Design/Evaluation 的模型调用，结果是否仍一样，能快多少？
- 你说学会了策略，哪个未见案例证明了迁移？
- 设计和校核共用工具，如何排除共同错误？
- 相比已有论文，你新增的机制在哪个实验中起作用？

## 9. 结题评审意见

**建议以“限定范围内可验证的工程交互与变更管理原型”作为当前定位，认可已有实施进展，要求补齐外部工程验证、同内核消融和真实效率数据后再评价方法优势。**

现阶段不建议继续以增加功能数量作为主线。最有价值的下一步，是把“做出了什么”转化为“在何种条件下，比哪个基线改善了什么、代价是什么”的证据。
